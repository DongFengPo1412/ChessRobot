## 視覚処理の開発

### 第1世代：位置検出と文字認識の分離

円の検出後に画像を切り出し、色と文字を判定する方式から開始しました。過去のローカルプロジェクト`PythonProject1`にはHough円検出と`ChessResNet18`があります。後者は事前学習済みResNet-18を1チャネル入力に変更し、256ユニットの隠れ層とdropoutを持つ11クラスの分類ヘッドを接続しています。

合成フォントで画像を生成できる一方、上方カメラのぼけ、反射、透視変形、小さな文字を十分に再現できませんでした。円検出の感度も照明に依存しました。これらの問題から実画像の収集に移行しました。初期コードは開発履歴の一部であり、このリポジトリにすべて含まれているわけではありません。

### 第2世代：実画像と多クラスYOLO

Chaoran Liuが実画像の収集と手動アノテーションを単独で担当しました。チーム記録では、40 × 40 cmの濃緑色の軟質盤で約500枚、その後35 × 35 cmのベージュ色盤で120枚を収集しました。盤の小型化は元の機構の到達範囲に対処しましたが、背景変化によるドメインシフトも生じました。

ローカルのデータは複数のRoboflowバージョンに書き出されています。その後、`PythonProject2`のラベル変換スクリプトで駒のクラスを1種類に統合し、位置検出を優先する方式に移行しました。

現在の[学習スクリプト](../recognition/train.py)には入力1280ピクセル、最大200エポック、batch size 4、GPU device 0を設定しています。回転、平行移動、拡大縮小、せん断、透視変換、反転、Mosaic、MixUp、erasing、copy-paste、HSV変動、分類損失の重み付け、ラベル平滑化を指定します。指定があることだけでは、各Ultralyticsバージョンとタスクで全処理が実際に適用された証拠にはなりません。再現にはパッケージ版、重み、データ、学習ログが必要です。

カメラから離れた小さな類似文字の識別は難しいままでした。駒の中心を盤面座標へ変換する処理と、文字画像を補正してから分類する処理は異なります。

### 第4世代：補正後の盤面分類

角点推定と正規化盤面の分類を組み合わせる開発方針です。

1. 本機の駒画像と空盤画像を準備。
2. 各交点に駒を合成し、対応するラベルを更新。
3. RTMPose/MMPoseベースのモデルで4隅を推定し、透視変換。
4. Swin Transformer V2と空間neck/headで90交点を16状態に分類。赤黒各7種、空点、その他/障害物。
5. 独立画像と連続系列を評価し、その後に局面管理と実機動作へ接続。

参考実装はOpenMMLabを基盤とする[TheOne1006/chinese-chess-recognition](https://github.com/TheOne1006/chinese-chess-recognition)です。`CChessMixSinglePngCls`、`CChess10_9Neck`、`CChessTableHead`が実装例になります。本プロジェクトのデータ、適応、学習、評価については、これらを基にチームが行った変更を具体的に示します。

参考実装の姿勢推定設定は`KLDiscretLoss`と`SoftWeightSmoothL1Loss`、Swin分類設定は`LabelSmoothLoss`を用います。異なる分岐を監督する損失です。

実機の入口は現在も第3世代を使用します。本リポジトリには第4世代の専用学習成果、評価記録、実機アダプタが含まれておらず、開発方針が学習や完全自律対局の完了を意味するわけではありません。

参考READMEの`full-err-zero = 0.83`は、その検証画像の83%で全交点が正解だったという意味です。全入力が誤りゼロという意味でも、本プロジェクトの実測値でもありません。

![盤面補正と独立した認識の例](images/vision_real_experiments.png)

補正・推論画面の例であり、表示された0.54 sは当該例の時間です。再現可能な遅延基準、全体の精度、ロボット統合の証拠にはなりません。

## 運動とハードウェア

### 盤面座標と動作目標

`control.py:board_to_physical`は列a–iをc = 0–8、行をr = 0–9とします。アームは黒側の底線後方にあり、a列がx正方向、遠方ほどyが増加します。横・縦の格子間隔をw、h、河界間隔をh_r、盤面オフセットをy_0、高さをz_bとすると、次式になります。

```math
x=(4-c)w,\qquad z=z_b,\qquad
y=y_0+\begin{cases}rh,&0\le r\le4\\4h+h_r+(r-5)h,&5\le r\le9\end{cases}
```

河界を独立に扱うことで、盤面全体を一様間隔の長方形とみなす誤差を避けます。視覚・棋局・アーム側の座標方向は`main.py:Coord`で変換し、画像の交点座標をそのままmm目標には使いません。

### 機構と補償

現在のリンク長は`L1 = 73`、`L2 = 231`、`L3 = 231`、`L4 = 66` mmです。格子間隔34.2 mm、河界34.0 mm、`BOARD_ORIGIN_Y = 200`、`BOARD_Z = −33`、`SAFE_Z = 70` mmです。設定値だけで全盤到達を証明することはできません。

有効な逆運動学は幾何計算前に次の経験的補償を適用します。

```text
comp_x = 1.125 * x
R_target = sqrt(comp_x² + y²)
R_comp = 0.94 * R_target
comp_z = z + 0.12 * R_target
delta_z = comp_z + L4 - L1
D = sqrt(R_comp² + delta_z²)
```

2リンクの到達条件を検証し、余弦定理で肩と肘の角度を求め、手首を下向きに拘束します。高さ項は距離に応じたフィードフォワードであり、同定された弾性モデルやフィードバック制御器ではありません。普遍的な配置精度や逆解計算時間は主張しません。

### 制御方式と設計上の選択

| 課題 | 実装方法 | 理由と対応範囲 |
| :--- | :--- | :--- |
| 固定リンクと下向きの先端姿勢 | 2リンクの幾何学的逆解、ベース角、手首姿勢の拘束。 | 固定構造を直接解ける方法で、最初に到達可能性を確認します。 |
| 伸展に伴う配置ずれ | 横・半径・高さ方向の経験的補償。 | 実機の偏差に合わせて調整でき、係数は機構と校正に依存します。 |
| 盤面付近での隣接駒との接触 | 安全高さでの搬送、8 mmの停止点、低速の垂直接近・退避。 | 経由点で接近方向を制約します。汎用的な障害物探索ではありません。 |
| 大きな指令変化と微小変位 | 直交座標の線形補間と0.1 mmの増分閾値。 | 移動を小刻みに分けます。S字速度計画は未実装です。 |

区間時間をT秒とすると、デッドゾーンを除いた補間は次式です。実際の周期には計算・通信・ホストのスケジューリング時間も加わります。

```math
N=\max(1,\lfloor50T\rfloor),\qquad
\mathbf{p}_i=\mathbf{p}_0+\frac{i}{N}(\mathbf{p}_{\mathrm{target}}-\mathbf{p}_0),\quad i=1,\ldots,N
```

軸ごとの総変位が0.1 mm以下なら、その軸のループ増分をゼロとし、区間末尾では目標点を再指令します。この値はソフトウェアの閾値であり、位置決め精度ではありません。接近・吸着・上昇・搬送・解放・退避の順に動作し、駒取りでは相手の駒を除去してから通常の搬送を再利用します。

<a id="mathematical-models"></a>

## 数学モデルとコードの対応

実装を理解するための主要な式をまとめます。コードの説明であり、精度、時間、信頼性を証明する評価ではありません。

### ホモグラフィと交点座標

カメラ画素の同次座標をp = (x, y, 1)、盤面をq = (u, v, 1)とします。4隅からHを推定し、同次座標を正規化して交点位置を求めます。ホモグラフィは平面の透視変形を補正しますが、レンズ歪みの校正を代替しません。

```math
\tilde{\mathbf{q}}=H\mathbf{p},\qquad u=\frac{\tilde q_1}{\tilde q_3},\quad v=\frac{\tilde q_2}{\tilde q_3}
```

### ROIと時系列安定化

ROIの各頂点を中心Cから半径方向へb = 60 px拡張します。中心座標EMAの係数は0.28で、現在は1.5 pxを超える変位時に更新します。離散交点位置は12フレームの最頻値を使い、エネルギーと個数の条件は前表に示しています。

```math
\mathbf{P}'_i=\mathbf{P}_i+b\frac{\mathbf{P}_i-\mathbf{C}}{\lVert\mathbf{P}_i-\mathbf{C}\rVert}
```

```math
\hat{\mathbf{c}}_t=(1-\lambda)\hat{\mathbf{c}}_{t-1}+\lambda\mathbf{c}_t,\qquad\lambda=0.28
```

### 解析逆運動学

前述の補償値からR = R_comp、z = delta_zとし、Dを肩から等価手首目標までの距離とします。2リンクの到達条件を確認して余弦定理を適用します。下式はラジアンで、コードは度へ変換してサーボ基準のオフセットを加えます。手首の追加補償係数は現在ゼロです。

```math
D=\sqrt{R^2+z^2},\qquad |L_2-L_3|\le D\le L_2+L_3
```

```math
\alpha=\arccos\frac{L_2^2+D^2-L_3^2}{2L_2D},\qquad\gamma=\arccos\frac{L_2^2+L_3^2-D^2}{2L_2L_3}
```

```math
\beta=\mathrm{atan2}(z,R),\quad q_2=\beta+\alpha,\quad q_3=q_2-(\pi-\gamma),\quad q_4=-\frac{\pi}{2}-q_3
```

### PWMと着手選択

PWM式のuは上下限に制限したマイクロ秒単位のパルス幅で、PCA9685のtickへ変換します。ネットワークはルールモジュールの候補集合M内で最大スコアを選択します。候補の妥当性は現在のルール実装範囲に依存します。

```math
n=\left\lfloor\frac{u}{20000}\times4096\right\rfloor,\qquad a^{\star}=\arg\max_{m\in\mathcal{M}} f(S)_{\mathrm{idx}(m)}
```

<a id="game-decision"></a>

## 局面管理と統合

`game/board.py`は盤面、駒の移動条件、候補手、手番切替、履歴リスト、将帥が失われた場合の終了を実装します。完全な終局判定や汎用の手戻しAPIはありません。候補手の検証範囲はこの実装に依存します。 自将への王手と将帥の対面を検査しますが、詰み、ステイルメイト、反復局面の完全な裁定は未実装です。

`ChessNet`は3 × 3の畳み込み3層（14 → 64 → 128 → 128）と全結合層（11,520 → 1,024 → 8,100）を持ちます。入力は14 × 10 × 9の駒位置テンソルです。出力インデックスは`(source_row * 9 + source_col) * 90 + destination_row * 9 + destination_col`で、ルールモジュールの候補から最大スコアを選びます。

現在の経路にMinimaxやAlpha–Beta探索はありません。学習済みスコアには`game/aaa.pth`が必要で、ない場合は候補からランダムに選びます。ネットワーク定義だけで学習済みの棋力を証明することはできません。

### 局面の符号化と候補手の絞り込み

14チャネルは紅黒各7種類に対応し、該当する駒の交点を1、他を0とします。交点はrow × 9 + column、行動はsource × 90 + destinationで符号化します。8,100次元には駒の移動規則に反する始終点の組も含まれます。

そのため全出力の最大値をそのまま選びません。先にルールモジュールで候補を生成し、その候補のlogitsだけを比較します。生のlogitsは順位付けのスコアで、正しい着手の確率として校正された値ではありません。明示的な移動制約と学習スコアを組み合わせ、多手先のゲーム木探索は行いません。

### 過去の棋譜による教師あり学習

チームのローカル発表資料にある`1ai(1).py`には、過去の学習処理が残っています。`CHESS_BOOKS`の棋譜を順に再生し、着手前の14 × 10 × 9局面と次の行動ラベルを作ります。畳み込み3層のネットワークで8,100行動を予測し、`CrossEntropyLoss`とAdamで学習します。関数の既定値は20エポック、バッチサイズ32、学習率0.001で、`chess_ai_model.pth`へ保存します。これらはコードの設定であり、学習完了や棋力評価の証拠ではありません。

logitsをz、棋譜の行動ラベルをt_i、バッチサイズをBとすると、交差エントロピーの目的関数は次式です。

```math
\mathcal{L}=-\frac{1}{B}\sum_{i=1}^{B}\log\frac{\exp z_{i,t_i}}{\sum_{k=0}^{8099}\exp z_{i,k}}
```

この過去のファイルは本リポジトリに同梱していません。層の名前と重みファイル名は現行`game/ai.py`と異なり、名前の変更だけで互換性は保証されません。別の`TianProject/game/ai.py`は畳み込み2層で、現行は3層と中間全結合層を使います。再現にはコード、学習データ、重み構造の対応が必要です。過去の教師あり学習と今後の自己対戦による強化学習は別の段階です。
